# Character facing and projected movement

## Symptom

The first 2.5D preview used character direction rows that did not face the projected movement direction.

## Evidence

`projection.ts` computes screen x = logical x − logical y and screen y = (logical x + logical y) / 2. Therefore down (+y) projects southwest, up (−y) northeast, right (+x) southeast and left (−x) northwest. Visual inspection of the generated original confirms the front pose faces southeast and the back pose northwest. The initial `character25d.ts` row order instead assigned southeast, northwest, northeast and southwest.

## Root Cause

The initial asset contract confused the logical navigation axes with the visible diagonals. It copied a direction description without deriving it from the actual projection function.

## Why the issue escaped detection

Asset checks validated hashes, alpha, crops and IDs, but did not compare character facing against projected movement. Type checking cannot detect an incorrect visual direction mapping.

## Proposed prevention

The runtime consumes an explicit direction mapping: down = reflected front, up = reflected back, right = front, left = back. A regression test compares each mapped facing vector to the actual projection of the corresponding logical unit movement. Desktop visual inspection remains necessary for pose quality and seating alignment.
